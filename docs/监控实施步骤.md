### 2.2 新建 `service/app/core/metrics/metrics.go`

```go
package metrics

import (
	"strconv"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
)

// UnmatchedRoute 是没有匹配到路由的请求统一使用的标签值。
// 绝不能用原始路径当标签：/api/v1/admin/submissions/123 这类会让标签基数爆炸，
// 最终把 Prometheus 内存打穿。
const UnmatchedRoute = "unmatched"

var (
	// 三个指标对应方案文档 4.1 的定义。
	httpRequestsTotal = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "xqyun_http_requests_total",
		Help: "按路由、方法与 HTTP 状态码统计的请求数。",
	}, []string{"method", "route", "http_status"})

	httpDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
		Name:    "xqyun_http_request_duration_seconds",
		Help:    "按路由统计的请求耗时。",
		Buckets: []float64{.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10},
	}, []string{"route"})

	businessResponses = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "xqyun_business_responses_total",
		Help: "按路由与业务码统计的统一响应数量。",
	}, []string{"route", "code"})
)

// ObserveHTTP 记录一次 HTTP 请求。route 必须传路由模板（c.FullPath()），
// 传空时归入 UnmatchedRoute。
func ObserveHTTP(method, route string, status int, seconds float64) {
	if route == "" {
		route = UnmatchedRoute
	}
	httpRequestsTotal.WithLabelValues(method, route, strconv.Itoa(status)).Inc()
	httpDuration.WithLabelValues(route).Observe(seconds)
}

// ObserveBusiness 记录一次统一响应的业务码。
// 本项目 HTTP 状态恒为 200，只有这里能拿到真实的业务成功 / 失败。
func ObserveBusiness(route string, code int) {
	if route == "" {
		route = UnmatchedRoute
	}
	businessResponses.WithLabelValues(route, strconv.Itoa(code)).Inc()
}
```

使用 `promauto` + 默认 registry，`go_*` / `process_*` 运行时指标会自动带上，以后做内存 / goroutine 监控不用再动代码。

### 2.3 新建 `service/middleware/http_metrics.go`

```go
package middleware

import (
	"context"
	"time"

	"github.com/cloudwego/hertz/pkg/app"

	"suki/xqyun/app/core/metrics"
)

// NewHTTPMetrics 记录每个请求的路由模板、方法、状态码与耗时。
// route 必须用 FullPath() 而不是 Path()，否则动态路由会变成每个 ID 一个标签。
func NewHTTPMetrics() app.HandlerFunc {
	return func(ctx context.Context, c *app.RequestContext) {
		start := time.Now()
		c.Next(ctx)
		metrics.ObserveHTTP(
			string(c.Method()),
			c.FullPath(),
			c.Response.StatusCode(),
			time.Since(start).Seconds(),
		)
	}
}
```

`c.FullPath()` 在中间件里已经可用——Hertz 的路由匹配在 handler chain 之前完成。

建议同时补一个单测 `service/middleware/http_metrics_test.go`，验证两点：动态路由记录的是模板而非原始路径；`/metrics` 不进入统计。

### 2.4 修改 `service/app/core/response/response.go`

三个输出函数各加一行，其余不动：

```go
import "suki/xqyun/app/core/metrics"

func SuccessWithMsg(c *app.RequestContext, data any, message string) {
	metrics.ObserveBusiness(c.FullPath(), CodeOK)   // 新增
	c.JSON(http.StatusOK, Body{
		Code:    CodeOK,
		Message: message,
		Data:    data,
	})
}

func Fail(c *app.RequestContext, code int, message string) {
	metrics.ObserveBusiness(c.FullPath(), code)     // 新增
	c.JSON(http.StatusOK, Body{
		Code:    code,
		Message: message,
	})
}

func FailWithData(c *app.RequestContext, code int, message string, data any) {
	metrics.ObserveBusiness(c.FullPath(), code)     // 新增
	c.JSON(http.StatusOK, Body{
		Code:    code,
		Message: message,
		Data:    data,
	})
}
```

`app/core/metrics` 不 import `response`，没有循环依赖。

**已知盲区**：不走这两个函数、直接写响应的接口只会计 HTTP 指标，不计业务码。当前只有留言 CSV 导出（`c.Data` 直出）属于此类。如果需要，在导出处理里补一行 `metrics.ObserveBusiness(c.FullPath(), response.CodeOK)`。

### 2.5 修改 `service/router.go`

```go
import (
	"github.com/cloudwego/hertz/pkg/common/adaptor"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

func customizedRegister(r *server.Hertz, app application.Application) {
	// /metrics 必须注册在 r.Use 之前。
	// Hertz v0.10.6 的 RouterGroup.handle 在注册时调用 combineHandlers，
	// 对当前中间件链做快照；先注册的 /metrics 不经过任何全局中间件，
	// 因此既不产生访问日志，也不会自己统计自己。
	r.GET("/metrics", adaptor.HertzHandler(promhttp.Handler()))

	r.Use(middleware.NewAccessLog())
	r.Use(middleware.NewHTTPMetrics()) // 新增

	r.GET("/ping", handler.NewPingController(app).Ping)

	// 以下保持不变
	router.RegisterUploadStatic(r, app.Upload())
	// ...
}
```

`adaptor.HertzHandler` 属于 Hertz 主仓库（`pkg/common/adaptor`），不是新增依赖。

保险起见，再给访问日志加一道跳过（防止以后有人调整注册顺序）：

```go
// middleware/access_log.go
func shouldLog(_ context.Context, c *app.RequestContext) bool {
	if p := c.FullPath(); p == "/ping" || p == "/metrics" {
		return false
	}
	// ... 其余不变
}
```

## 3. 对方案文档的三处修正

落地时核对出的偏差，已回写 `docs/监控方案.md`：

| 位置 | 原方案写法 | 正确做法 | 原因 |
| --- | --- | --- | --- |
| Grafana 环境变量 | `GF_SERVER_HTTP_ADDR: 127.0.0.1` | **删除该变量** | 容器内绑回环后，Docker 端口映射（DNAT 到容器 eth0）访问不到。对外不可见应由宿主机侧 `127.0.0.1:3001:3000` 保证 |
| backend 端口 | `"${BACKEND_PORT:-8888}:8888"` | `"127.0.0.1:${BACKEND_PORT:-8888}:8888"` | 原写法绑 `0.0.0.0`，`/metrics` 会随 8888 一起暴露到公网 |
| 部署形态 | 独立 `docker-compose.monitoring.yml` + `-f` 叠加 | **主 compose 内用 `profiles: ["jk"]`** | 叠加文件需要人肉合并网络 / 变量插值 / 服务覆盖规则，落地时踩过 `external` 网络首次部署失败；`profiles` 是 Compose 原生机制，命令更短、语义更清楚 |

### 4.2 修改 `docker-compose.yml`

监控服务直接写在主文件里，用 `profiles: ["jk"]` 标记为可选。默认 `docker compose up -d` 不启动它们；`docker compose --profile jk up -d` 才启用。

两处改动：

**1. backend 端口改绑回环**

```yaml
    ports:
      # 只绑定回环：Nginx 与前端都走 Compose 内网，宿主机端口仅用于调试。
      # 不要改回 "8888:8888"，否则 /metrics 与后端接口会暴露到公网。
      - "127.0.0.1:${BACKEND_PORT:-8888}:8888"
```

**2. 末尾新增两个服务**

```yaml
  # ===== 监控（可选，profile: jk）=====
  # 默认 `docker compose up -d` 不启动这两个服务。
  # 启动监控：docker compose --profile jk up -d
  # 只停监控：docker compose stop prometheus grafana
  #
  # 首次启动前：
  #   mkdir -p data/monitoring/prometheus data/monitoring/grafana
  #   chown -R 65534:65534 data/monitoring/prometheus
  #   chown -R 472:472     data/monitoring/grafana
  #   在 .env 设置 GRAFANA_PASSWORD
  prometheus:
    image: prom/prometheus:v3.15.0
    profiles: ["jk"]
    restart: unless-stopped
    volumes:
      - ./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ./data/monitoring/prometheus:/prometheus
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.path=/prometheus
      - --storage.tsdb.retention.time=7d
    ports:
      - "127.0.0.1:9090:9090"

  grafana:
    image: grafana/grafana:12.4.0
    profiles: ["jk"]
    restart: unless-stopped
    environment:
      # 不用 ${GRAFANA_PASSWORD:?...}：Compose 对全文插值，
      # 即使没启用 profile，缺变量也会让普通 `docker compose up -d` 失败。
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD:-}
      GF_USERS_ALLOW_SIGN_UP: "false"
    volumes:
      - ./monitoring/grafana/provisioning:/etc/grafana/provisioning:ro
      - ./monitoring/grafana/dashboards:/var/lib/grafana/dashboards:ro
      - ./data/monitoring/grafana:/var/lib/grafana
    ports:
      - "127.0.0.1:3001:3000"
```

> **为什么不用独立叠加文件**：`docker compose -f a -f b` 需要人肉合并网络、变量插值和服务覆盖规则，落地时已踩过 `external` 网络首次部署失败的问题。`profiles` 是 Compose 原生机制，同一份文件、同一条命令。
>
> **不要设置 `GF_SERVER_HTTP_ADDR=127.0.0.1`**：容器内绑回环后，Docker 端口映射（DNAT 到容器 eth0）访问不到；对外不可见由宿主机侧 `127.0.0.1` 绑定保证。
>
> 服务同处项目默认网络（`xiaoque_default`），Prometheus 直接抓 `backend:8888`，不需要额外声明 `networks`。

改端口映射必须重建容器才生效（`restart` 不重新映射）。

### 7.1 三个面板

新建 Dashboard，三个面板类型均为 **Time series**：

```promql
# 面板 1：全站 QPS
sum(rate(xqyun_http_requests_total[1m]))

# 面板 2：按接口分组的 QPS（Legend 用 {{route}}，Stacking 开启）
sum by (route) (rate(xqyun_http_requests_total[1m]))

# 面板 3：业务成功 / 失败 QPS（Legend 用 {{code}}）
sum by (code) (rate(xqyun_business_responses_total[1m]))
```

建议时间范围默认 `Last 6 hours`、刷新间隔 `30s`。

### 7.2 看板入库

面板调好后 Dashboard → Share → Export → Save to file，存为：

```
deploy/docker/xqyun/monitoring/grafana/dashboards/qps.json
```

提交后，其他环境重建 Grafana 时会自动装载。文件名不要改，provisioning 按目录递归加载。

### 7.3 第一期不配告警

QPS 没有普适的「正常值」，峰谷差异大。先观察 1–2 周建立基线，再在第四期定阈值与推送渠道。

## 8. 日常运维

### 8.1 启动 / 停止 / 更新

```bash
# 启动整套（业务 + 监控）
docker compose --profile jk up -d

# 只起业务（不带监控）
docker compose up -d

# 只更新后端（例如改了埋点代码）
docker compose up -d --force-recreate backend

# 只重启监控
docker compose restart prometheus grafana

# 只改 Prometheus 配置：编辑 monitoring/prometheus.yml 后
docker compose restart prometheus
```

### 8.2 停止监控（不要用 down）

```bash
# ✅ 只停监控容器
docker compose stop prometheus grafana

# ❌ 绝对不要这样：会连同 MySQL / Redis / 后端 / 前端一起停掉
# docker compose down
```

### 8.3 回滚

监控与业务解耦，回滚互不影响：

| 场景 | 操作 |
| --- | --- |
| 埋点代码有问题 | 重新编译上一版 `xqyun` 二进制覆盖，`docker compose up -d --force-recreate backend`；`/metrics` 消失只会让 Prometheus 抓取失败，不影响业务 |
| 监控容器起不来 | `docker compose stop prometheus grafana`，业务无感；排查完 `docker compose --profile jk up -d` 重新拉起 |
| 端口绑定出问题 | 把 `docker-compose.yml` 的 backend `ports` 改回 `"${BACKEND_PORT:-8888}:8888"` 并重建；**同时**确认 `/metrics` 不能被公网访问，可用防火墙限制该端口 |

### 8.4 数据清理

Prometheus 自动按 7 天保留，无需手工处理。`data/monitoring/prometheus` 若异常膨胀，先检查标签基数（`/api/v1/.../prometheus/tsdb/status` 或 `prometheus_tsdb_head_series` 指标），不要直接删目录。

## 附录 A：内存不足时替换为 VictoriaMetrics

只改两处，PromQL 与看板不用动：

`docker-compose.yml` 中的 prometheus 服务替换为：

```yaml
  victoriametrics:
    image: victoriametrics/victoria-metrics:v1.115.0
    profiles: ["jk"]
    restart: unless-stopped
    command:
      - -storageDataPath=/victoria-metrics-data
      - -retentionPeriod=7d
      - -promscrape.config=/etc/prometheus/prometheus.yml
    volumes:
      - ./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ./data/monitoring/victoriametrics:/victoria-metrics-data
    ports:
      - "127.0.0.1:8428:8428"
```

Grafana 数据源 URL 改为 `http://victoriametrics:8428`。内存占用约 50MB。
