# 权限控制方案（Casbin · URL 策略）

> 状态：**设计稿，2026-11-11 定稿，尚未实现**。当前后台接口只校验登录状态（`middleware/admin_auth.go`），所有登录账号拥有全部后台权限。本文档确定二期实现 RBAC 时采用 Casbin，届时按第 9 节顺序落地。
>
> 适用范围：管理后台 `/api/v1/admin/**`。官网前台是公开接口（渲染、站点配置、表单提交），不引入权限判定；表单提交靠限流而非权限。

---

## 1. 为什么用 Casbin

| 方案 | 评价 |
| --- | --- |
| 手写 `role → []rule` 映射 + 中间件 | 角色、策略要做到后台可配置、频繁调整时，等于自己维护一套策略增删改查与缓存，收益不高 |
| OPA | 能力更强，但要额外部署服务与下发策略，对单后台 CMS 过重 |
| **Casbin** | Go 库，进程内判定，策略落 MySQL；RBAC 模型直接表达「角色能访问哪些 URL / 方法」；将来加数据范围（ABAC）、多站点（domain）不用换框架 |

结论：采用 **`github.com/casbin/casbin/v3` + `github.com/casbin/gorm-adapter/v3`**，判定在进程内完成，不新增任何服务。

依赖版本（2026-11-10 查询 `@latest`，使用当前最新稳定版）：

| 模块 | 版本 | 要求 Go |
| --- | --- | --- |
| `github.com/casbin/casbin/v3` | `v3.11.0` | 1.13 |
| `github.com/casbin/gorm-adapter/v3` | `v3.41.0` | 1.24.0 |

项目当前 Go 1.25.7，两者均兼容。升级时重新确认最低 Go 版本（参考监控依赖 `client_golang` 因要求 Go 1.26 而锁版的先例）。

> 注意大版本：`gorm-adapter v3.41.0` 的代码 import 的是 **`github.com/casbin/casbin/v3`**（`go.mod` 要求 ≥ v3.8.1），因此本项目必须用 Casbin v3，**不要同时引入 v2**——v2 与 v3 是两套类型，`Enforcer` 与 adapter 不兼容。

## 2. 设计决策摘要

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 判定对象 | **URL 路由模板 + HTTP 方法**（`obj = c.FullPath()`，`act = c.Method()`） | 策略直接对应接口，不需要权限码目录、URL 映射表与双向校验，概念最少 |
| 唯一权威 | Casbin 策略表 `xqyun_casbin_rule` | 授权只看策略；角色配置页、`/me`、审计都以策略为准 |
| 策略存储 | 单表 `xqyun_casbin_rule`，由 Casbin 管理 | 不双写业务表，避免两处数据不一致 |
| 角色元数据 | 保留 `xqyun_roles`（code / name / description / is_system），只存展示信息 | 后台角色管理页需要中文名与内置角色保护 |
| 用户-角色 / 角色-权限关系 | 只存 Casbin 的 `g` / `p` 规则，**不建** `xqyun_user_roles`、`xqyun_role_permissions` | 关系由 Casbin 读写，避免三套数据 |
| 认证与授权 | 分成两个中间件：`AdminAuth` 认人，`Permission` 认权 | 职责单一；登录、刷新、退出不经过权限中间件 |
| 自助接口 | `/admin/me`、`/admin/user/profile`、`/admin/user/password` 放在独立子组，**只挂 `AdminAuth`、不挂 `Permission`** | 登录即可访问；不用为每个角色（含未来新角色）各写一条策略 |
| 权限来源 | 每次请求实时查 Casbin（内存判定），**不写进 JWT** | 改角色立即生效，不用等 Access Token 过期；内存判定开销可忽略 |
| 策略加载 | 启动时 `LoadPolicy`；保存角色 / 权限后重新加载 | 当前单实例；将来多实例加 Redis watcher |
| 超管 | `p, super_admin, /api/v1/admin/*, *` | 一条规则覆盖全部后台接口，新增路由自动可用 |
| 前端 | `/me` 返回 `"METHOD 路由模板"` 字符串，前端按同一字符串判断按钮 | 前端不需要 ID，也不会接触数据库策略 |
| 范围 | 仅后台接口 | 前台公开接口不接权限 |

### 2.1 与「权限码 + 映射表」方案的取舍

之前的设计是「权限码作唯一权威，URL 在代码里查表映射到权限码」。改纯 URL 后的变化：

- **少一层概念**：权限码目录、URL 映射表、双向校验全部去掉；策略本身就是 `(角色, URL, 方法)`。
- **少一处同步**：新增同权限接口时，只需给角色加策略，不用先改映射再改策略。
- **代价一：前端要维护「按钮 → 路由模板」常量**。按钮没有页面 ID，`hasPermission` 只能比对模板字符串（`POST /api/v1/admin/pages/:id/publish`）；这是纯 URL 方案必须接受的成本。
- **代价二：策略条数变多**。一条业务能力可能对应多条路由，角色配置页展示的是 URL 行；为了不跨能力边界放开，非超管角色逐条配置，不用 `/pages/*` 这类前缀通配（见 5.2）。
- **代价三：改路由要改策略**。改路径、加 `/v2`、拆接口时，数据库里的旧策略会失效或悬空，需要同步迁移；这一点比权限码方案重。

## 3. Casbin 模型

模型文本以 Go 常量维护（`service/app/core/authz/model.go`），不额外部署 `.conf` 文件，单测与运行时共用同一份。装配方式：`model.NewModelFromString(modelText)` 得到 model，再 `casbin.NewEnforcer(model, adapter)`。

```ini
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && keyMatch(r.obj, p.obj) && (p.act == "*" || r.act == p.act)
```

说明：

- `sub`：当前登录用户 ID（字符串），取 JWT 的 `sub`；
- `obj`：**路由模板**，取 `c.FullPath()`，如 `/api/v1/admin/pages/:id`，不是 `/pages/12`；
- `act`：HTTP 方法，取 `string(c.Method())`；
- `g`：用户 → 角色的继承关系，`g(1, super_admin)` 表示用户 1 属于超管；
- `p`：角色 → URL 模板 → 方法，`p(publisher, /api/v1/admin/pages/:id, PUT)`；
- `keyMatch` 只用于 `*` 通配：`p, super_admin, /api/v1/admin/*, *` 覆盖全部后台接口；其余策略按模板**精确匹配**；
- 方法支持 `*`（`p.act == "*"` 时匹配任意方法），读接口可以合并成一条；
- 方法统一大写（`GET` / `POST` / `PUT` / `DELETE`），与 `c.Method()` 的返回值一致；策略里写小写会匹配不上。

### 3.1 为什么用 `c.FullPath()` 而不是实际路径

- 策略里写的是路由模板（`/pages/:id`），`FullPath()` 返回的也是模板，两边字符串一致，**精确匹配**即可判定，不需要 `keyMatch2` 把 `:id` 解释成正则。
- 避免误授权：如果用实际路径 + `keyMatch2`，策略 `/api/v1/admin/submissions/:id` 会同时匹配实际路径 `/api/v1/admin/submissions/export`（`export` 也满足 `[^/]+`），查看权限会顺带拿到导出权限。用模板精确匹配不会出现这个问题——`FullPath()` 对 export 返回的是静态路由 `/submissions/export`，与 `:id` 策略不相等。
- 路由模板由 Hertz 在匹配阶段确定，中间件里读取没有额外开销。

### 3.2 路由注册顺序

权限判定按 `FullPath()` 精确匹配，不再依赖注册顺序；但**静态路径仍要注册在 `:id` 之前**，否则 `/submissions/export` 会命中 `:id` 的 handler，行为错误（虽然权限判定本身仍按 `/submissions/export` 模板走）。现有 `router/admin.go` 已把 `/submissions/export`、`/submissions/unread-count` 放在 `:id` 之前，新增类似路径时保持这个顺序。

## 4. 策略存储

### 4.1 `xqyun_casbin_rule` — Casbin 策略表

由 [`gorm-adapter`](https://github.com/casbin/gorm-adapter) 读写，**业务代码不要直接 SQL 增删规则**，统一走 Casbin API（`AddPolicy` / `AddPolicies` / `RemovePolicy` / `RemoveFilteredPolicy` / `AddGroupingPolicy` …），保证内存策略与数据库一致。

| 字段 | 类型 | 空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `ptype` | `VARCHAR(100)` | 否 | `''` | 规则类型：`p` 权限规则 / `g` 用户角色关系 |
| `v0` | `VARCHAR(100)` | 否 | `''` | `p`：角色 code；`g`：用户 ID |
| `v1` | `VARCHAR(100)` | 否 | `''` | `p`：URL 路由模板；`g`：角色 code |
| `v2` | `VARCHAR(100)` | 否 | `''` | `p`：HTTP 方法（`GET` / `POST` / `PUT` / `DELETE` / `*`） |
| `v3` | `VARCHAR(100)` | 否 | `''` | 预留（domain 等） |
| `v4` | `VARCHAR(100)` | 否 | `''` | 预留 |
| `v5` | `VARCHAR(100)` | 否 | `''` | 预留 |

索引：

- `PRIMARY KEY (id)`
- `UNIQUE KEY idx_xqyun_casbin_rule (ptype, v0, v1, v2, v3, v4, v5)` — 与 gorm-adapter 默认唯一索引一致

示例数据：

| ptype | v0 | v1 | v2 | 含义 |
| --- | --- | --- | --- | --- |
| `p` | `super_admin` | `/api/v1/admin/*` | `*` | 超管拥有全部后台接口 |
| `p` | `publisher` | `/api/v1/admin/pages/:id` | `PUT` | 发布管理员可保存页面草稿 |
| `p` | `editor` | `/api/v1/admin/pages/:id` | `GET` | 内容编辑可查看页面详情 |
| `g` | `1` | `super_admin` | | 用户 1（初始 admin）属于超管 |

约定：

- 用户 ID 用字符串，与 JWT `sub` 一致；角色用 `code` 而不是数字 ID，策略可读、导出方便；
- 角色 `code` 创建后**不可修改**（只能改 `name` / `description`），否则要重写全部 `p` / `g` 规则；
- 建表走 golang-migrate（`migration/时间戳_create_xqyun_casbin_rule.up.sql`），符合「表结构以迁移文件为准、不启用 GORM AutoMigrate」的约定。
- `gorm-adapter v3.41.0` 默认在构造函数里 AutoMigrate。初始化顺序固定为：
  1. `gormadapter.TurnOffAutoMigrate(db)` 关闭自动建表；
  2. `gormadapter.NewAdapterByDBUseTableName(db, "", "xqyun_casbin_rule")` 复用 `application` 已有的 GORM 连接。
- adapter 自动建表时使用的唯一索引名是 `idx_` + 表名（即 `idx_xqyun_casbin_rule`），迁移文件里按同名创建，两者一致。
- `v1` 的长度是 100，当前最长路径（`/api/v1/admin/submissions/unread-count`，38 字符）足够；以后路径变长时先改字段长度再上线。

### 4.2 与 `xqyun_roles` 的关系

- `xqyun_roles` 只保留角色展示信息（`code` / `name` / `description` / `is_system`），**不再关联** `xqyun_user_roles` / `xqyun_role_permissions`；这两个表从表设计中移除。
- 角色列表接口：读 `xqyun_roles`，再用 `enforcer.GetFilteredPolicy(0, code)` 取该角色的策略（`[角色, URL, 方法]`）聚合返回。
- 新建角色：写 `xqyun_roles` 一行，再用 `AddPolicies` 写入策略。
- 更新权限：`RemoveFilteredPolicy(0, code)` 清空该角色旧策略，再 `AddPolicies` 写入新策略；两步在同一用例内，任一步失败返回错误，不破坏已加载的内存策略。
- 删除角色：先 `RemoveFilteredPolicy` 与 `RemoveFilteredGroupingPolicy` 清掉规则，再删除角色行；`is_system = 1` 的角色禁止删除。规则清理失败则不删角色。
- 重命名角色：只允许改 `name` / `description`，不允许改 `code`。

## 5. 策略设计

### 5.1 粒度原则

- `super_admin` 只用一条通配策略：`p, super_admin, /api/v1/admin/*, *`。
- 其他角色**逐条列 URL + 方法**，不用 `/api/v1/admin/*`、`/pages/*` 这类前缀通配：前缀会把同一模块的发布、删除接口一起放开，直接破坏「编辑不能发布」这条核心约束。
- 方法为 `*` 只用于「该路径下所有方法都要给」的情况；当前内置角色没有这种场景，`super_admin` 除外。
- 策略不区分语言、站点，也不看资源归属；将来需要「编辑只能改自己建的页面」时，再按 3 节的扩展方式加 ABAC，不提前设计。

### 5.2 当前路由的策略清单（种子）

`super_admin` 由一条通配策略覆盖，下表只列另外三个角色。✓ = 需要写入一条 `p` 策略；实现时以 `router/admin.go` 的实际路由为准，新增路由要同步补表。

| 路由模板 | 方法 | `publisher` | `editor` | `viewer` |
| --- | --- | --- | --- | --- |
| `/api/v1/admin/pages` | GET | ✓ | ✓ | ✓ |
| `/api/v1/admin/pages` | POST | ✓ | ✓ | |
| `/api/v1/admin/pages/:id` | GET | ✓ | ✓ | ✓ |
| `/api/v1/admin/pages/:id` | PUT | ✓ | ✓ | |
| `/api/v1/admin/pages/:id` | DELETE | ✓ | ✓ | |
| `/api/v1/admin/pages/:id/translate` | POST | ✓ | ✓ | |
| `/api/v1/admin/pages/:id/publish` | POST | ✓ | | |
| `/api/v1/admin/pages/:id/unpublish` | POST | ✓ | | |
| `/api/v1/admin/menus` | GET | ✓ | ✓ | ✓ |
| `/api/v1/admin/menus/:code` | GET | ✓ | ✓ | ✓ |
| `/api/v1/admin/menus/:code` | PUT | | | |
| `/api/v1/admin/settings` | GET | ✓ | ✓ | ✓ |
| `/api/v1/admin/settings` | PUT | | | |
| `/api/v1/admin/media` | GET | ✓ | ✓ | ✓ |
| `/api/v1/admin/media/upload` | POST | ✓ | ✓ | |
| `/api/v1/admin/media/:id` | GET | ✓ | ✓ | ✓ |
| `/api/v1/admin/media/:id` | PUT | ✓ | | |
| `/api/v1/admin/media` | DELETE | ✓ | | |
| `/api/v1/admin/media/:id` | DELETE | ✓ | | |
| `/api/v1/admin/submissions` | GET | ✓ | ✓ | |
| `/api/v1/admin/submissions/export` | GET | ✓ | | |
| `/api/v1/admin/submissions/unread-count` | GET | ✓ | ✓ | |
| `/api/v1/admin/submissions/:id` | GET | ✓ | ✓ | |
| `/api/v1/admin/submissions/:id/status` | PUT | ✓ | | |

说明：

- 登录即可的接口（`GET /admin/me`、`PUT /admin/user/profile`、`PUT /admin/user/password`）不在这张表里，它们走独立子组，不进权限中间件。
- 站点设置、导航保存、留言导出、留言状态、素材删除只给 `publisher` 及以上的部分，`editor` 看不到这些入口；`viewer` 只有读接口。
- 二期的内容库、账号管理、角色管理、审计日志接口按同一方式追加策略（`content:*` 那批接口上线时逐条补）。

### 5.3 策略与路由的一致性

纯 URL 方案没有映射表，策略直接写路由模板，因此要注意：

- **模板必须和 `c.FullPath()` 完全一致**：`/api/v1/admin/pages/:id`，不能写成 `/pages/:id`、`/api/v1/admin/pages/:pageId`（`keyMatch` 只认 `*` 通配，参数名不同会匹配不上）。
- **默认拒绝**：没有匹配策略就是 `40300`。新增路由对非超管角色默认不可见，这是 fail-closed；上线新功能时要记得给对应角色补策略，否则运营会反馈「按钮点了没权限」。
- **改路由要迁移策略**：路径改名、拆接口、加版本前缀时，旧策略会失效或悬空；改路由的同一批改动里要写迁移清理旧策略、写入新策略。
- 自动校验能做的只有「超管覆盖全部路由」和「策略里的路径都能匹配到某个已注册路由模板」；后者在实现时加一个测试：遍历 `route.Engine.Routes()`，断言每条 `p` 的 `v1`（除 `*` 通配）都能在路由模板集合里找到。找不到说明是悬空策略（路由删了策略没删），直接让测试失败。反过来「每条路由是否有角色可访问」不做强制断言——新接口只给超管是合法状态。

## 6. 拦截流程

```
请求
  │
  ▼
AdminAuth（middleware/admin_auth.go）   // 校验 Bearer Token，失败 40100
  │  写入 xqyun.admin.claims（含 sub）
  ├─────────────── 自助接口（/me、改资料、改密码）→ handler
  ▼
Permission（middleware/permission.go）  // 调 Casbin
  │  · Enforce(sub, c.FullPath(), string(c.Method())) == false → 40300
  │  · Enforce 执行出错 → 50000
  ▼
handler
```

判定过程（伪代码）：

```go
sub := claims.Subject
allowed, err := m.enforcer.Enforce(sub, c.FullPath(), string(c.Method()))
if err != nil {
    hlog.CtxErrorf(ctx, "权限判定失败：%v", err)
    response.Fail(c, response.CodeInternal, "权限判定失败")
    c.Abort()
    return
}
if !allowed {
    response.Fail(c, response.CodeForbidden, "没有操作权限")
    c.Abort()
    return
}
c.Next(ctx)
```

- 权限中间件挂在 `router/admin.go` 的受保护子组上，位于 `AdminAuth` 之后；自助接口放在另一个子组，只挂 `AdminAuth`。
- **先 `Use` 再 `Group`**：Hertz 的 `Group` 在创建子组时复制父组已有的中间件，所以要先给 `authorized` 挂 `AdminAuth`，再分出「自助子组」和「受保护子组」；顺序反了会漏掉认证，自助组等于裸奔。
- 判定在资源查询之前，不区分「资源不存在」与「无权限」，避免用来探测资源。
- `sub` 直接取 claims 的 `Subject`，不用前端传入。
- 每次请求只做一次内存判定，不访问 MySQL / Redis。
- enforcer 是进程内单例，按项目惯例挂在 `Application`（如 `app.Authz()`）上，由 `bootstrap` 启动时装配；中间件、`/me` 与角色管理用例都通过它读写策略，不各自 new。

## 7. 接口与前端

- `GET /admin/me`：返回 `AdminUser`（结构见 `Go后端接口设计.md` 4.1）。
  - `roles`：`GetRolesForUser`；
  - `permissions`：`GetImplicitPermissionsForUser` 返回 `[角色, URL, 方法]`，后端拼成 `"METHOD URL"` 字符串（去掉角色列、去重），例如 `"PUT /api/v1/admin/pages/:id"`；如果用户命中的策略包含 `*`（超管），返回 `["*"]`。
- `POST /admin/auth/login`：登录成功后同样填充 `roles` / `permissions`，前端不用额外请求即可渲染首屏；之后以 `/me` 为准。
- 前端（`admin/`）：
  - 会话 store 保存 `permissions`，提供 `hasPermission(rule)`：`*` 直接放行，否则判断是否包含 `"METHOD URL"`。
  - 按钮常量在前端集中维护，例如 `const PAGE_PUBLISH = 'POST /api/v1/admin/pages/:id/publish'`；**这是纯 URL 方案必须接受的成本**：路由模板改了，前端常量要同步改。
  - 无权限的菜单项、按钮、操作列做隐藏 / 禁用；页面级入口可加路由守卫，但**前端显隐不是安全边界**，后端判定才是。
  - 角色管理页按模块分组展示「URL + 方法」勾选项（如「页面」「素材」「留言」），勾选后提交策略列表；接口只接收 URL 与方法，不接受权限码。
- 不新增响应码：无权限使用已有的 `40300`（`Go后端接口设计.md` 第 1 节）。

## 8. 内置角色

内置角色沿用 `MySQL数据库表设计.md` 的四个，`is_system = 1`，不允许删除：

| code | 名称 | 策略 |
| --- | --- | --- |
| `super_admin` | 超级管理员 | `p, super_admin, /api/v1/admin/*, *`（一条通配） |
| `publisher` | 发布管理员 | 5.2 表中 `publisher` 列的所有行 |
| `editor` | 内容编辑 | 5.2 表中 `editor` 列的所有行（不能发布） |
| `viewer` | 只读 | 5.2 表中 `viewer` 列的所有行 |

- 初始 admin 账号写入 `g, 1, super_admin`。
- 四个角色由迁移写入 `xqyun_roles` 与 `xqyun_casbin_rule`，种子见 5.2。
- `publisher` 是「内容编辑 + 发布」；`editor` 可编辑不能发布（对应「审批流先用角色权限替代」）；`viewer` 只读。
- 站点设置、导航保存、素材删除、留言导出等敏感操作只给 `publisher` / 超管。

## 10. 注意事项与风险

- **默认拒绝会隐藏新接口**：新增路由对非超管角色默认 `40300`，必须同时补策略；建议把「新增后台路由的检查清单」写进提交模板（路由 → 角色策略 → 前端按钮常量 → 接口文档）。
- **策略粒度**：非超管角色不要用 `/api/v1/admin/*`、`/pages/*` 前缀通配，否则会把发布 / 删除一起放开；逐条列 URL + 方法。
- **前端常量同步**：按钮判断用 `"METHOD URL"` 字符串，路由模板改名时前端常量必须同步，否则按钮消失或报 403；这是纯 URL 方案的固有成本。
- **改路由要迁移策略**：路径改名 / 拆接口时，旧策略要么删掉要么迁移；测试会抓「策略 URL 匹配不到路由」的悬空项。
- **策略与内存一致性**：只通过 Casbin API 改策略；保存成功后 `LoadPolicy()`，失败则返回错误并保留旧策略（内存里仍是旧规则，行为可预期）。
- **多实例**：当前只有一个后端容器，重新加载即可；扩到多副本时加 Redis watcher（Casbin 官方 `watcher/redis-watcher`）或用发布事件触发各实例重载。
- **停用账号**：`status = 0` 目前只在登录 / 刷新时校验，Access Token 最长还能用 15 分钟。接 RBAC 时一并考虑：`AdminAuth` 之后可加账号状态检查（缓存到 Redis）或缩短 Access Token。
- **不把权限写进 JWT**：JWT 里的权限会随角色变更变旧；只在 `/me` 与登录响应里返回快照，真正判定走 enforcer。
- **gorm-adapter 的 AutoMigrate**：与「表结构以迁移文件为准」的约定冲突，按 4.1 用 `TurnOffAutoMigrate` 关闭；升级 adapter 版本时确认该函数与默认索引命名没变。
- **版本锁定**：`casbin/v3 v3.11.0`、`gorm-adapter/v3 v3.41.0`。升级前确认最低 Go 版本仍 ≤ 项目版本（`gorm-adapter` 目前要求 Go 1.24.0），不要像 `client_golang` 那样升到要求更高 Go 的版本；同时确认 adapter 仍依赖 v3 大版本。
- **依赖体积**：casbin 会带入少量间接依赖，二进制略增大，可接受。
- **审计**：权限变更（授权、取消）应写 `xqyun_audit_logs`（二期与审计日志一起做）。
