# 小鹊云监控方案（QPS 优先）

> 状态：**方案已确定，尚未实施**（2026-10-31）
> 范围：先只做 Go 后端 QPS，后续按阶段扩展
> 相关：本文只记录设计，落地前需要确认文末「待确认事项」

## 一、目标与边界

第一阶段只回答一个问题：**每个接口现在每秒被调用了多少次、成功还是失败。**

不做的事（现阶段明确不纳入）：

- 不做链路追踪（接口总数十几个，收益低）
- 不做业务 BI 看板
- 不做日志检索（后续阶段再考虑 Alloy / Loki）
- 不做 Grafana 直连 MySQL 的实时查询（每次刷新跑 SQL，会拖库）

## 二、技术选型

原则：只使用当前仍在积极维护的组件。

| 组件 | 选型（2026-10-31 核对） | 用途 | 状态 |
| --- | --- | --- | --- |
| 指标存储 | Prometheus **3.15.x** | 抓取、存储、PromQL | 3.15.0 于 2026-09-24 发布，3.16 仍在 rc |
| 展示 | Grafana **13.x** | 看板 | 13 为当前主线（稳定 13.0.x） |
| Go 埋点 | `github.com/prometheus/client_golang` **v1.24.1** | 生成 `/metrics` | 官方 SDK |
| 网关埋点（二期） | nginx-prometheus-exporter **v1.5.1**（读取 `stub_status`） | 全站 QPS | 官方，活跃 |

**版本兼容性注意**：

- `client_golang` v1.25.0 起要求 **Go ≥ 1.26**，本项目 `service/go.mod` 当前为 `go 1.25.7`，因此锁定 **v1.24.1**。升级 Go 工具链后才能跟进 v1.25。
- Prometheus 镜像使用 `prom/prometheus:v3.15`，Grafana 使用 `grafana/grafana:13`，避免 `latest` 标签随上游滚动导致行为变化。

**关于 `hertz-contrib/monitor-prometheus`**：该官方 contrib 包仍在维护（Snyk 标记 maintenance healthy），但社区活跃度低，且指标只带 `method` / `statusCode` 标签，**无法区分业务 `code`**，同时需要额外占用一个监听端口（默认 `:9091`）。本项目仍采用「自定义中间件 + client_golang」，约 20 行代码，可控性更高。

**拉取式仍是官方推荐**：`client_golang` 官方文档明确 `promhttp` 拉取式采集为默认推荐方案，OTLP 推送仅作为补充（适用于批处理或无法被抓取的场景）。因此「Prometheus 抓取 + client_golang」不属于过时技术栈。

**明确不采用**（已废弃或停更）：

| 技术 | 原因 |
| --- | --- |
| `grafana/agent` | 已于 **2025-11-01 EOL**，继任者为 Grafana Alloy |
| Promtail | 已于 **2026-03-02 EOL**，替代方案为 Grafana Alloy |
| Grafana StatsD / Graphite 数据源 | 老一代方案 |
| `nginx-module-vts` | 第三方 Nginx 模块，需自行编译镜像，与本项目「官方镜像 + 挂载产物」的部署方式冲突 |
| InfluxDB 1.x + Telegraf | 生态老化，不支持 PromQL |

## 三、QPS 数据来源

分两层，第一阶段只做应用层。

| 层 | 数据源 | 能看到什么 | 阶段 |
| --- | --- | --- | --- |
| 应用层 | Go 后端 `/metrics` | 仅 API 请求：`render/page`、登录、上传、留言提交 | **第一期** |
| 网关层 | Nginx `stub_status` | 全站请求，含静态资源与 `/uploads/` 视频 | 第三期 |

先做应用层的原因：QPS 真正有价值的业务口都在 API 侧；Nginx 层数字会被静态资源和视频请求严重稀释。

## 四、埋点设计

### 4.1 指标定义

```text
xqyun_http_requests_total{method, route, http_status}     counter
xqyun_http_request_duration_seconds{route}                histogram
xqyun_business_responses_total{route, code}               counter
```

### 4.2 三个关键约束

1. **`route` 必须使用路由模板，不能用原始路径。**
   Hertz 的 `c.FullPath()` 返回 `/api/v1/admin/submissions/:id` 这类模板；若直接用 `c.Path()`，每个页面 ID / 留言 ID 都会变成独立标签，标签基数爆炸，Prometheus 内存会被打穿。

2. **QPS 必须按业务 `code` 拆分。**
   本项目统一响应是 **HTTP 200 + `{code}`**，HTTP 状态码恒为 200，按 HTTP 状态统计没有信息量。业务成功 / 失败的量要在统一响应封装（`response.Success` / `response.Fail`）里计数，那里是唯一知道业务 `code` 的地方。

3. **`/metrics` 不挂进 `/api/v1`，也不暴露到公网。**
   直接在 `customizedRegister` 里注册 `r.GET("/metrics", ...)`，只允许 Compose 内网访问，不经 Nginx 转发到 80 端口。访问日志中间件需要跳过该路径，否则每 15 秒产生一条日志。

### 4.3 代码量

- HTTP 指标中间件：约 20 行，只依赖 `client_golang`，不引入 hertz-contrib 的监控中间件（少一个依赖，行为更可控）
- 统一响应封装：增加约 2 行计数器
- 路由注册：1 行

## 五、部署形态

使用**独立 compose 文件**叠加启动，主文件 `docker-compose.yml` 不做修改。

```yaml
# deploy/docker/xqyun/docker-compose.monitoring.yml
services:
  prometheus:
    image: prom/prometheus:v3.15
    restart: unless-stopped
    volumes:
      - ./data/monitoring/prometheus:/etc/prometheus
      - ./data/monitoring/prometheus-data:/prometheus
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.retention.time=7d
    ports:
      - "127.0.0.1:9090:9090"
    networks: [xiaoque_default]

  grafana:
    image: grafana/grafana:13
    restart: unless-stopped
    volumes:
      - ./data/monitoring/grafana:/var/lib/grafana
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD}
      GF_SERVER_HTTP_ADDR: 127.0.0.1
    ports:
      - "127.0.0.1:3001:3000"
    networks: [xiaoque_default]

networks:
  xiaoque_default:
    external: true
```

启动命令：

```bash
cd deploy/docker/xqyun
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d
```

要点：

- Compose 项目名为 `xiaoque`，实际网络名是 `xiaoque_default`，用 `external: true` 加入后才能抓到 `backend:8888`
- Prometheus 与 Grafana **只绑定 `127.0.0.1`**，通过 SSH 隧道访问 `http://127.0.0.1:3001`
- 保留 7 天足够；该量级一天指标数据不足 100MB

## 六、看板

第一期三个面板即可。

```promql
# 1. 全站 QPS
sum(rate(xqyun_http_requests_total[1m]))

# 2. 按接口分组的 QPS（堆叠图）
sum by (route) (rate(xqyun_http_requests_total[1m]))

# 3. 业务成功 / 失败 QPS
sum by (code) (rate(xqyun_business_responses_total[1m]))
```

Grafana 配置 Prometheus 数据源 + 一个 Time series 面板即可出图。

**第一期不配置告警**：QPS 没有普适的"正常值"，峰谷差异大，需要先观察一到两周建立基线，再定阈值。

## 七、资源占用

| 组件 | 内存 |
| --- | --- |
| Prometheus | 约 120MB |
| Grafana | 约 200MB |
| 合计 | 约 320MB |

若服务器内存余量不足，可将 Prometheus 换为 VictoriaMetrics 单二进制（约 50MB，PromQL 兼容），代价是周边生态工具较少。

## 十、其他可选监控项（暂不实施，备查）

按「是否真的会导致站点故障」排序，供后续排期参考：

| 优先级 | 监控项 | 说明 |
| --- | --- | --- |
| P0 | 磁盘使用率（>80% 警告 / >90% 紧急） | 视频单文件 200MB、日志最多约 3GB、MySQL 数据持续增长；磁盘满是单机部署最常见的第一杀手 |
| P0 | 容器存活 / 重启次数 | 现有 healthcheck 只服务 Compose，无人收到通知；Node OOM、后端 panic 需靠此项发现 |
| P0 | HTTP 可用性（首页 / `/admin/` / `/ping`） | 网关、Nuxt、后端任一挂掉，表现一致但都应立即知晓 |
| P0 | 内存使用率 / OOM | MySQL 8 + Node + Go 三者共享内存 |
| P1 | 业务错误率（`code != 0` 占比） | 统一响应导致 Nginx 层 5xx 监控完全看不到业务错误 |
| P1 | 接口 P95 延迟 | 官网每次打开页面需调用三个接口 |
| P1 | Nginx 5xx / 502 | 曾出现过浏览器侧 `/api/backend/**` 502 问题 |
| P1 | Redis 内存与 evicted keys | Redis 存储刷新令牌，被淘汰表现为用户无故掉线 |
| P1 | MySQL 连接数 | 接近 `max_open_conns=50` 后所有接口一起超时 |
| P2 | 慢查询、上传失败率、留言积压、登录失败次数 | 有余力再做 |

### 零容器兜底方案（可选）

在正式监控就绪前，可用 cron + shell 脚本实现磁盘 / 容器 / HTTP 三项检查，仅在状态变化时推送告警（避免每 5 分钟刷屏）。该方案不依赖任何容器，可作为长期兜底。
